# Component ids the LIVE game server is known to fail to initialize, and why.
#
# tools/check-game-server.sh reads this file. An id that fires in production and
# is NOT listed here fails the check at COUNT 1 - because every new entity type
# this server has ever grown announced itself as an id nobody had a branch for,
# and that is cheap to notice on the first one and expensive on the ten-thousandth.
#
# This file is a LEDGER OF DEBT, not a mute button. Three rules:
#
#   1. A line must say what the id IS. A number with the word "known" next to it
#      is not an entry; it is the silence this replaced wearing a hat.
#   2. Where the consequence is not yet established, the line says UNINVESTIGATED
#      and that is honest. It is not the same claim as "harmless".
#   3. An id that gets FIXED - a seed written, or an absence declared in
#      ComponentAbsencePolicy - is DELETED from this file, not commented out. A
#      baseline that only ever grows is the thing this replaced.
#
# Measured 2026-08-19 against the live journal (which reaches back to 08-08).
# Every one of these rides a BEST-EFFORT interest batch
# (failOnComponentInitError: false), which is why not one "[error] DROPPING the
# whole AddComponent batch" line appears anywhere in that journal: nothing has
# lost its 190602 TransformState to one of these, and nothing is sitting at the
# world origin because of them. If a DROPPING line ever does appear it is a
# different and far worse event, and the rate check will show it.
#
# Component names are from docs/component-ids.md.
#
# THE NUMBER TO EXPECT. Measured over a live 3-hour window before the fix in
# "Stop the server telling its own log that its gaps are unfixable": 119 errors
# over 503 interest batches = 23.7 per 100. That fix removes 68 of the 119
# (1013 seeded; 1120/8066/1259/1304/4323 declared absent), so a healthy window
# should now read roughly 10 per 100. The default ceiling of 25 therefore allows
# a 2.5x regression before it complains - loose on purpose, because the sharp
# instrument here is the unknown-id check, which fires at count one.
#
# Format: <component id> <name> - <what is lost, or UNINVESTIGATED>

# --- island fauna: the creature simulation this server does not run ----------
# The client asks every spawned creature for the full retail creature stack. We
# spawn fauna as decoration. Each of these leaves one client visualizer disabled.
#
# ALL SIX ARE CANDIDATES FOR ComponentAbsencePolicy and are deliberately NOT
# there yet. The client audit (2026-08-19) found every reader either disabled or
# null-guarded, none of them in an IdComponentToEntityMap, and a jellyfish fully
# animated without any of them (JellyFishAnimationClient has no [Require] at all,
# so it runs regardless). Two caveats stopped this from being a drive-by
# declaration, and both are about MANTA RAYS, which IslandFaunaPolicy does spawn:
#   1160 - MantaRayMaterialExpressionClient has NO [Require], so it Updates every
#          frame and multiplies the manta's emissive by GetHealthAsRatio(), which
#          returns -1 with no reader. No exception; the manta's glow inverts.
#   1175 - the manta's Animator keeps playing its default entry state, but loses
#          every parameter drive (banking, wing speed). It renders; it does not
#          respond.
# So the honest move is to SEED a health value and 1175's booleans for mantas,
# and declare the other four absent - which belongs to whoever owns fauna, with
# a manta in front of them. Until then these are known, not fine.
1154 ConductPickerState - creature AI conduct selection; no behaviour tree runs here
1160 HealthState - creature health; nothing can damage or kill our fauna
1166 AgeState - creature ageing; our fauna do not grow
1171 MortalityState - creature death; our fauna cannot die
1172 TirednessState - creature fatigue; our fauna do not tire
1175 AnimationControllerFSIMState - the FSIM-side animation driver, which retail ran in the creature sim we do not have

# --- built/atlas ship states with no server model ----------------------------
